O workshop de hoje Antes do modelo, a decisão.

Como preparar um projeto de IA e escolher onde o Jev entra.

→ avança · F tela cheia · N notas
Apresentação (2 min). Quem sou, o que faço e o combinado do dia: este não é um workshop sobre um modelo. É sobre as decisões que a gente toma antes de escolher o modelo, e o Jev é o caso que vamos usar para praticar. Navegação: setas, F para tela cheia, N para estas notas.

Tudo começa com uma pergunta

“Qual região vendeu
mais este ano?”

Uma pergunta. Seis etapas até a resposta.
Quantas delas precisam de um LLM?

Gancho (2 min). Leia a pergunta em voz alta e pare. É uma pergunta real do nosso golden set (q-029). Peça um palpite no chat: de seis etapas, quantas precisam de um LLM? Não responda agora. A resposta é o último slide.

O problema

Os primeiros carros eram carruagens sem cavalo.

Toda tecnologia nova nasce com a forma da antiga. A IA nasceu com a forma do chat: educada, articulada, feita para uma pessoa ler.

Carruagem (3 min). Conte a história: os inventores tiraram o cavalo, puseram um motor e mantiveram o banco alto, as molas e até o suporte do chicote. É o que fazemos quando colocamos um chat no meio do backend. O modelo foi treinado para ser um assistente agradável; isso é ótimo com um humano do outro lado, e ruim quando o leitor é um if.

O problema

Quem lê a resposta quase nunca é uma pessoa.

99%máquina com máquina
1% humano
“Computadores já fazem muito só ramificando em bits. Imagine se também ramificassem em bom senso, entendimento e intenção.”Manifesto da TypeSafe AI · a proporção 99/1 é a aposta da empresa, não uma medição
99/1 (3 min). A aposta da TypeSafe: automação em escala é 99% interação máquina com máquina e 1% com humano. Deixe claro que é uma aposta deles. O ponto que importa para nós: se o leitor é código, a saída precisa ter tipo, ser rápida e dizer o quanto confia. Pergunte: no sistema de vocês, quantas respostas de LLM alguém realmente lê?

A virada

Três jeitos de construir software

Software tradicionalRegras confiáveis, compostas em árvore. Não entende texto livre.
AgentesO modelo escolhe o próximo passo. Cada volta é uma chance de descarrilar.
Software com IAO código é dono do fluxo. A IA entra só em decisões pequenas e restritas.
Arquiteturas (4 min). Leia a figura da esquerda para a direita. Tradicional: tudo auditável, mas cego para linguagem. Agente: funciona bem com alguém olhando, e cada loop adiciona risco. Software com IA: o fluxo continua sendo código, e o modelo aparece só onde é preciso bom senso sobre dado não estruturado. É a terceira que vamos construir hoje.

Erro composto (3 min). A conta é simples: 0,95 × 0,95 × … Seis etapas a 95% dão 74%. Dez dão 60%. Por isso a pergunta de projeto não é "qual o melhor modelo", é "quantas etapas eu preciso mesmo entregar a um modelo, e como eu sei quando ele errou". Diga que a conta é ilustrativa.

A regra (5 min). Este é o slide para fotografar. A ordem importa: código primeiro, porque é de graça e não erra. Depois decisão tipada. LLM só onde há texto para uma pessoa. As cores deste slide (cinza código, ciano Jev, âmbar LLM, lilás humano) se repetem até o fim. Faça um exercício rápido: "dias de atraso maior que 30" é o quê? Código. "Este e-mail pede senha?" Decisão. "Escreva a resposta ao cliente." LLM.

Fontes: docs.typesafe.ai e o pricing.yaml do projeto (jev-1.13.0). Latência declarada pelo fabricante; a nossa a gente mede na demo.

Jev (4 min). Primeiro System One Model da TypeSafe. Não gera texto, não conversa, não chama ferramenta. Recebe um estado e perguntas tipadas e devolve valores que o código usa direto. Três tipos: choice (uma opção da lista), score (nota numa rubrica), noul (probabilidade de uma afirmação ser verdadeira). A saída só pode ser uma das opções dadas: não existe rótulo inventado. Os números são do fabricante; não defenda, diga que vamos medir.

O modelo

Treinado para decidir, não para agradar

Treino (3 min). RLHF (Reinforcement Learning from Human Feedback) otimiza a resposta que as pessoas preferem: foi o que criou o ChatGPT. RLVR otimiza tarefas verificáveis: modelos de raciocínio, fortes e caros. RLCD (Reinforcement Learning for Calibrated Decisions) é o caminho do Jev: a recompensa é sobre a decisão e sobre dizer a probabilidade certa. Curiosidade: um dos fundadores da TypeSafe é coinventor do RLHF.

O modelo

Quem aprende a agradar desaprende a duvidar.

Calibrado quer dizer: a probabilidade bate com a taxa de acerto.

quando diz0,2
acontece cerca de 20% das vezes
quando diz0,8
acontece cerca de 80% das vezes
Calibração (3 min). Otimizar preferência humana estreita a distribuição: o modelo fica com um jeito só de responder e soa confiante sempre (mode dropping). Para automação isso é o problema central: um modelo que acerta 95% e não avisa quando está nos 5% não deixa você tirar o humano do loop. Calibração é o que transforma a probabilidade em algo que o código pode usar. Vale para grupos de previsões, não é garantia sobre uma resposta isolada.

Agora, a parte difícil

O modelo é a parte fácil.

Difícil é decidir onde ele entra.
E provar que valeu a pena.

Pivô (1 min). Mudança de marcha. Até aqui foi o "o quê". Daqui em diante é o "como": o que fizemos antes de escrever código, como escolhemos onde o Jev entra e como montamos uma comparação que não dá para contestar.

O projeto

O que existia antes da primeira linha de código

O golden set e o replay foram a primeira SPEC implementada: sem gabarito e sem reprodução, não existe comparação.

Preparação (6 min). A ordem é a história. Primeiro o PRD, com o problema e o que fica fora. Depois o passo 0: repositório, CI, CLAUDE.md com as regras para o agente de código. Depois as SPECs, cada uma com critério de aceite testável. E a primeira SPEC implementada não foi um provider nem o grafo: foi o golden set e o replay. Antes de ter modelo, a gente já tinha o gabarito e um jeito de rodar sem chave. Mostre a pasta docs/specs no repositório.

O projeto

A regra aplicada: seis etapas, três donos

01guardraildecisão

3 noul: injection, dado sensível, fora de escopo

02triagedecisão

1 choice, 8 opções: 7 views ou nenhuma

03toolcódigo

SELECT na view do registro

04replygeração

redige a resposta com os dados

05verifydecisão

3 noul: fiel, responde, inventa número

06actcódigo

limiares: libera, revisa ou bloqueia

2etapas de código: consulta e regra de ação
3etapas de decisão: Jev e LLM disputam, e a gente mede
1etapa de geração: só LLM, sem disputa
O mapa (6 min). Passe a pergunta do gancho por cada etapa. Guardrail: é injection? Tem dado sensível? Está fora do escopo? Triage: qual das 7 views responde (ou nenhuma)? Tool: código puro, o nome da view vem do registro, nunca do modelo. Reply: LLM escreve, e só com os dados da view. Verify: a resposta é fiel? Inventou número? Act: código decide entre liberar, mandar para revisão ou bloquear. O nó reply existe de propósito: mostra onde o Jev não compete.

O projeto

Uma definição, dois modelos, a mesma régua

7 perguntas tipadas, escritas uma vez. Nenhum prompt por modelo.

Comparação justa (5 min). A decisão de design mais importante do projeto. O mesmo NodeSpec (quais campos do estado entram, quais perguntas, quais critérios) alimenta os dois providers. No modo "both" os dois rodam em paralelo; só o primário decide a aresta do grafo, e os dois resultados ficam registrados. Assim o grafo não bifurca e a comparação é pergunta a pergunta. As 7 perguntas: 3 do guardrail, 1 da triagem, 3 da verificação. Exceção documentada: o modo "native" (SPEC-12) dá ao LLM um system prompt por etapa, para medir contra um LLM bem instruído.

A régua (4 min). Decida o que medir antes de ver qualquer resultado. Regras do projeto: tokens vêm da resposta da API, latência do relógio monotônico, preços do arquivo de configuração com data e fonte. O que a gente não mede, a gente não afirma. E o PRD diz com todas as letras: o objetivo não é provar que o Jev é melhor. O projeto mede; a conclusão é de quem roda.

Padrão 1 · fan-out especulativo

Pergunte tudo de uma vez.

Ticket de suporte
1 requisição · 5 perguntas avaliadas em paralelo
choiceQual a categoria?
scoreQual a severidade do bug?
noulTem passos para reproduzir?
noulPede reembolso?
scoreQuão frustrado está?
Seu códigousa o que importa e ignora o resto
No projetoguardrail faz 3 perguntas numa chamada. verify faz outras 3.
Fan-out (4 min). As perguntas em cinza são especulativas: severidade só importa se for bug, reembolso só se for cobrança. Mesmo assim vão todas na mesma chamada, porque são avaliadas em paralelo e quase não mudam o tempo de resposta. O código descarta o que não serve. Com LLM isso seria uma chamada depois da outra, ou um prompt gigante. Exemplo da documentação da TypeSafe.

No projetoguardrail ≥ 0,70 bloqueia · triage < 0,80 → humano · fiel < 0,80 ou inventa ≥ 0,30 → humano
Confiança (5 min). O exemplo da documentação é um banco por voz aprovando uma transferência: abaixo de 0,6 vai para um atendente; entre 0,6 e 0,85 o sistema confirma com o usuário; acima de 0,85 aprova. Consultar saldo, que tem risco baixo, passa com 0,6. O limiar acompanha o risco da ação. No nosso projeto os limiares estão no graph.yaml e são arquivo protegido: mudar um deles muda o resultado da comparação. E limiar não se copia: calibra-se com os próprios dados, olhando o dashboard.

Padrão 3 · score composto

O modelo responde as partes. O peso fica no código.

45%pede credencial?
30%remetente não bate?
25%prêmio inesperado?
risco_spam = 0.45 * pede_credencial + 0.30 * remetente_nao_bate + 0.25 * premio_inesperado

Mudou a prioridade? Troca um coeficiente, não um prompt.

No projetoverify não pergunta “a resposta está boa?”. Pergunta 3 coisas pequenas, e o act combina.
Score composto (4 min). A documentação chama a decomposição de "provavelmente o conceito mais importante". Uma pergunta ampla ("é spam?") esconde vários julgamentos numa resposta só. Perguntas atômicas expõem cada julgamento, e você inspeciona, ajusta e combina no código. O exemplo dos pesos 45/30/25 vem do guia de triagem da TypeSafe. Outro exemplo deles: triagem de currículos com pesos diferentes para IC sênior e para gestor, usando as mesmas quatro notas.

Padrão 4 · roteamento por intenção

Classifique antes de gastar.

No projetotriage escolhe 1 de 7 views, ou nenhuma. O nome da view vem do registro em código, nunca do modelo.
Intenção (4 min). Nem todo pedido precisa do mesmo tratamento. Alguns se resolvem com uma consulta ao banco, outros precisam de um LLM com contexto específico, outros de uma pessoa. Um classificador rápido e barato na frente faz o recurso caro ser usado só quando precisa. No nosso projeto a triagem é exatamente isso, e tem uma regra de segurança junto: nada que o modelo devolve vira SQL.

A prova

Agora, no código.

A mesma pergunta, dois modelos.
Resposta, latência, tokens e custo, lado a lado.

Roteiro: (1) docs/PRD.md e docs/specs em 2 minutos; (2) specs.py: as 7 perguntas tipadas; (3) playground com a pergunta do gancho, modo both, abrindo cada etapa; (4) uma pergunta adversarial para ver o guardrail bloquear; (5) lote e dashboard. Honestidade

Onde o Jev não entra

Escrever

Texto, conversa, código. No nosso fluxo, o reply.

→ LLM

Raciocinar em cadeia

Pergunta ampla, que pesa vários fatores de uma vez.

→ decomponha, ou LLM

Regra exata

Se um if resolve, modelo nenhum faz melhor.

→ código

E limiar copiado de slide não vale: calibre com os seus dados.

Limites (3 min). Ser honesto aqui dá credibilidade ao resto. O Jev não gera texto, não conversa, não escreve código, não faz tool calling. É um modelo proprietário, servido por API, em acesso antecipado. E os números de fabricante são de fabricante: por isso o projeto existe.

Para levar

Para levar (3 min). Três perguntas, na ordem do workshop: o problema, o método, a prova. Peça para responderem a primeira no chat agora. O repositório fica público como ferramenta: dá para trocar o golden set pelo seu caso e rodar a mesma comparação.
